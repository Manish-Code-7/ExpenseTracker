# Neon setup

Run these against your Neon branch, in order:

| File | What it does | Required? |
|---|---|---|
| `migrations/0000_init.sql` | Tables, enums, constraints, indexes (generated by `drizzle-kit`) | Yes |
| `02_functions.sql` | Integrity triggers + recurring detection | Yes |
| `03_rls.sql` | Row Level Security via `pg_session_jwt` | Optional |

Apply the migration with `npx drizzle-kit migrate` (uses `DATABASE_URL`), then
paste `02_functions.sql` and `03_rls.sql` into the Neon SQL Editor.

## RLS / JWKS

`03_rls.sql` is defence in depth: every tRPC procedure already filters by the
signed-in user, so the app is correct without it. Enabling it means a bug in
that layer still can't read another user's rows.

1. Deploy so `https://YOUR-APP/api/auth/jwks` is publicly reachable.
2. Neon Console → your project → **Settings → RLS → Add Authentication Provider**,
   paste that JWKS URL.
3. Run `03_rls.sql`.
4. Set `DATABASE_AUTHENTICATED_URL` to the `authenticated` role's connection
   string. Until you do, `dbForUser()` falls back to the owner connection and
   the policies simply don't apply.

The JWT is minted by Better Auth's `jwt` plugin (`src/server/auth.ts`) with the
user id in `sub`, which is what `auth.user_id()` reads.

## The nightly scan

`pg_cron` isn't available the way it was on Supabase. `detect_recurring_patterns_all()`
is there for a scheduler to call — a Vercel Cron or GitHub Action hitting an
endpoint that runs it. The in-app "Scan now" button works regardless.
